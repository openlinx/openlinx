## Context

See proposal.md (Why) for the motivation. The approach is shaped by these constraints:

- **`020-add-crawl-core`** (its groups 4 and later, page preparation and the executor seam among them, are not coded yet; this draft follows its design):
  - **Page preparation** (`020` D9) is `prepare_page(url, response, settings)` in `spider.crawl.pages`, one pure, module-level function of a URL, its `FetchResult` and the settings snapshot, `PageSettings`, that its worker received once at start (the robots token, `--strip-params`, the `ScopeRules`, and the settings that registered extractors read, such as `030`'s `content_area`). It decodes, parses once, runs the link extractor, the registered extractors and the robots directives parser, and returns one frozen msgspec record, `PreparedPage`. `PageInput` sits beside it in `spider.crawl.pages`.
  - **The executor seam:** the engine calls `await executor.prepare(url, response)` on the `PageExecutor` of the `CrawlContext` (`020` D15), a Protocol in `spider.crawl.pages`, where `020`'s `InProcessExecutor` calls `prepare_page` on the loop's thread. `020` ships the in-process executor; this change plugs a process pool in behind the same seam without touching the engine.
  - **`Hooks`** (`020` D9) is a frozen dataclass of tuples in the `CrawlContext`: extractors, per-response handlers and post-crawl passes, listed by `default_hooks()` in `spider.services.hooks`, the composition root. Extractors are module-level functions from the parsed tree and a `PageInput` to a msgspec struct, so a worker process imports them by name. Per-response handlers turn a `UrlResult` into store rows; they run in the crawl process for every URL that reaches a final state, so they stay there. A test adds its own extractors and handlers to `default_hooks()` and passes them to the Crawl Service.
  - **The link extractor** returns `DiscoveredLink` values with a non-nullable normalised target (a malformed reference is dropped) and an `ordinal`, the Link's place in document order. It takes an `is_internal: Callable[[NormalizedUrl], bool]` and imports nothing of the Scope; page preparation passes the one built from the snapshot's `ScopeRules`.
  - **`ScopeRules`** holds strings only and pickles to about 134 bytes. The Public Suffix List behind `subdomains` is loaded lazily, once per process, on the first lookup (about 56 ms), so each worker that needs it loads it once.
  - **`parse_error`** already lists `worker_crashed` and `parse_timeout` for this change (`020` D18). Both keep `parsed` = 0, because nothing came out of the worker; a registered extractor that raises inside page preparation is not a crash, and `020` records it as `parsed` = 1 with `extractor_error`, following the Page's Links (the user's decision of 2026-10-14), and the `StopSignal` gives requests in flight a grace period of 10 seconds.
- **ADR-0006:** page preparation's per-response records, which cross the pool (`DiscoveredLink`, extractor outputs, the page-preparation record) or are built beside them in the worker (`PageInput`), are frozen `msgspec.Struct`s. They cross the process boundary as they are, and pickle about twice as fast as slotted dataclasses.
- **Platforms:** Windows only has `spawn`. Python 3.14 changes the default start method on Linux to `forkserver`. `fork` in a process with threads is unsafe on macOS.
- **`060-add-crawl-control`** starts background Crawls with CREATE_NO_WINDOW, which is approved.
- **The pool is unconditional in v0.1** (the user's decision of 2026-10-11). The benchmark measures and sizes it; it does not decide whether it is built.

## Goals / Non-Goals

**Goals:**
- Measure first: a baseline of the in-process executor at ~500k URLs, before any pool code.
- The same page preparation and extractor code runs in workers, unchanged, and behaves identically on every OS.
- Bounded memory, crash containment, and a clean shutdown.

**Non-Goals:**
- Parallel fetching, which is already asyncio.
- Tuning flags. The worker count is automatic in v0.1.

## Decisions

### D1. Own `spawn` worker processes behind `020`'s seam
- **The workers:** `n` processes started with `multiprocessing.get_context("spawn")`, each with its own pipe, that prepare one Page at a time.
- **Their number:** `n = max(1, cores − 2)`, the verdict of the writer prototype of 2026-10-11 on the maintainer's laptop (8 physical cores, 6 workers). `cores` is `psutil.cpu_count(logical=False)`, or `os.cpu_count() // 2` when psutil cannot tell, and when the process may run on only some logical CPUs (`os.process_cpu_count()` from Python 3.13, psutil's CPU affinity before it; taskset, a container's cpuset), as many physical cores as its share of them. On Linux a cgroup v2 CPU quota caps those cores: `cpu.max` of the process's cgroup and of each ancestor up to the root, `ceil(quota / period)` CPUs, `max` for none, the lowest counting, so `docker --cpus=2` or a Kubernetes limit of 2 on a 16-core host gives 1 worker, not 14 that oversubscribe its CPU and memory (cgroup v1 is not read). On Windows before Python 3.13 `n` is at most 62: `multiprocessing.connection.wait` waits on at most 63 handles there (3.13 batches its waits), and the waiter watches each worker's result pipe and its own wake pipe, so 63 workers would fail every Page. `psutil` is a runtime dependency imported inside `spider.crawl.parse_pool`, never on the startup path (`tests/cli/test_startup.py`). The re-run after `080` sweeps smaller counts and may lower the default (D6).
- **The pool executor** implements `020`'s `PageExecutor.prepare(url, response)`: it hands the URL and its response to an idle worker, or queues it until one is idle, and awaits the page-preparation record. One thread of the crawl process waits on every worker's result pipe with `multiprocessing.connection.wait`, with a timeout at the nearest deadline (D8), and resolves the awaiting futures on the event loop. A worker's end is the end of file on its result pipe: only the worker holds that pipe's write end, as the crawl process closes its copy once the worker has started and `spawn` hands no other worker a handle of it, so the waiter watches no process sentinels (ruled 2026-10-14). The engine and the extractors do not change.
- **The settings snapshot (`PageSettings`) and the registered extractors** (by reference) are the first message on a worker's task pipe, so they reach each worker once; the worker starts with its two pipe ends as its only arguments. A worker that has read its snapshot answers "ready" before its first Page, and one that cannot read it, such as one that cannot import an extractor's module, answers with the error and ends; a worker that ends before it is ready is a Crawl error (`WorkerStartError`), never replaced (ruled 2026-10-14).
  - *Why not a start argument:* on Windows `multiprocessing` sends a pipe end to a `spawn` child as a handle duplicated into the parent, which the child takes over (`DUPLICATE_CLOSE_SOURCE`) only when it unpickles that argument (`multiprocessing.reduction.DupHandle`, `multiprocessing.connection.reduce_pipe_connection`). A child that died while it unpickled the snapshot, before its pipes, left the result pipe's write end open in the crawl process, so the waiter saw no end of file and the Page waited for good (the first red of task 2.8 hung for its 30 s timeout). With the pipe ends as the only arguments, the child holds them before any extractor's module is imported. POSIX passes the descriptors at exec, so it had no such gap.
  - A work item is then only the fetched response, so the snapshot is never pickled once per response. The worker's loop keeps them in local variables for its life, so the worker module holds no state. Each worker sets SIGINT to ignored (SIGBREAK too, on Windows) when it starts. The pool starts its workers when it gets its settings snapshot, after the Seed's Redirect Chain has ended (022 D3: the Scope may widen at its end), never with an earlier Scope.
  - *Alternative:* `functools.partial(prepare, snapshot)` per submit. It pickles the snapshot, its compiled patterns and the extractor list with every response. Rejected.
- **Why own workers rather than `concurrent.futures.ProcessPoolExecutor`:** the executor knows which worker holds which Page and since when, so it can end exactly the worker over its deadline (D8) and charge a crash to exactly one URL (D3).
  - *Alternative:* `ProcessPoolExecutor`, recreated after a crash or a deadline. It needs less code of ours, but it cannot end one worker (3.14's `kill_workers()` ends them all), so every timeout would end every worker and resubmit their Pages, paying about 1 second of `spawn` on Windows each time; it marks a future as running when the item enters its call queue, not when a worker takes it, so a deadline could not start at the take; and one dead worker fails every pending future, which needs a serial phase to find the culprit. Rejected: the code it saves moves into workarounds.
- **Why `spawn` everywhere:** one start method means one behaviour to test. The cost is paid once per Crawl, and once per replaced worker: about 1 second on Windows while a worker imports selectolax and the extractors, overlapped with the rest of the Seed's request and robots.txt, but not with the Seed's own preparation: the snapshot exists only once the Seed's chain has ended (022 D3).
- *Alternative:* `forkserver` on POSIX. It is faster to start, but it behaves differently per OS. Rejected.
- *Alternative:* threads. selectolax releases the GIL only partly, and pure-Python extractors would still contend. Rejected.

### D2. The work item and the bounded queue
- **The work item:** the URL and its `FetchResult`, as `prepare_page` takes them. The result is the `PreparedPage`, as the in-process executor returns it, which the engine hands to the per-response handlers in the crawl process.
- **Bounded queue:** the engine keeps a semaphore of `cap + 2 × n` permits, where `cap` is `020`'s global request cap, `min(100, max(20, 4 × concurrency))`. As `020` builds it (its task cap), each URL holds a task slot from its dispatch to its submit to the writer, and there are `cap + backlog` slots, where the executor's `backlog` is `2 × n` for the pool and 0 in process; the requests themselves stay under `cap`. A slot is held by every dispatched URL, so this is stricter than a permit per request (decided 2026-10-14). Fetching therefore waits whenever page preparation falls behind.
- **On one host the bound is the same:** `--concurrency` limits a host's requests in flight, but a URL gives back its host slot when its fetch ends and keeps its task slot until its submit, so `cap + 2 × n` fetched Pages may wait for preparation, whatever the host count. Holding the host slot until the Page is prepared would bound one host to `--concurrency + 2 × n`, but a slow Page would then stop fetching from its host while workers sit idle (ruled 2026-10-14: the spec's bound is `cap + 2 × n` on one host too).

### D3. Crash containment
A worker that dies (a segfault in a native parser, or `os._exit`) closes its result pipe, which the waiter sees as its end of file (D1). The executor then:
1. records the one Page that worker held as `worker_crashed`
2. starts a replacement worker with the same snapshot
3. goes on; no other Page is touched, because each worker holds one Page at a time

Each crash therefore costs one URL and one worker start.
- **A failure Page, never an exception:** `prepare()` returns `PreparedPage(parse_error="worker_crashed", parse_error_message=...)`, with no Links of the document and no outputs, for a Page whose worker ended and for one whose outcome the crawl process cannot read; `020` records it with `parsed` = 0 and still reads the response's header Links itself (its task 7.23). `prepare()` raises only for a programmer's error, such as a Page before `start()`, for a pool that cannot start its workers (`WorkerStartError`, D1), and for the exception page preparation itself raised, which reaches the engine as it would in process (ruled 2026-10-14).
- **Each output crosses on its own:** a worker sends the Page without its outputs and each output pickled by itself, so an output the crawl process cannot unpickle, such as one whose class cannot be rebuilt there, costs only its extractor, recorded as `extractor_error` with the Page's Links kept, as an output the worker cannot pickle does (`020` D16); only a Page whose own record cannot be read is `worker_crashed` (ruled 2026-10-14). The cost is one more pickle per output.
- **The replacement** starts off the event loop's thread, as the first workers do, and the Pages waiting meanwhile wait for it; the waiter thread watches the pipes of the workers alive at each wait, so it runs until the pool closes, not until its first workers have ended. A replacement that ends before it is ready breaks the pool with `WorkerStartError` (D1), so a worker that cannot start is never started again and again. `close()` waits for a replacement still starting, then stops it with the others.
- *Alternative:* recording every Page in flight as `worker_crashed`, as a broken `ProcessPoolExecutor` would. That punishes innocent URLs. Rejected.

### D4. Shutdown
- **Normal end and stop:** on a normal end, and on a stop (an interrupt, or `060`'s stop request), the engine stops submitting and waits for the Pages in flight, as part of the grace period `020`'s `StopSignal` gives requests in flight. The executor then sends each worker a stop message and joins it. A worker still preparing a Page when the grace period ends is killed, and that URL stays `queued`, as `020` leaves a request cancelled before its submit. Workers ignore SIGINT, so a console Ctrl+C reaches only the crawl process, which ends the workers in order.
- **A second interrupt,** which calls `os._exit(130)` in `020`: the workers see their pipe close and exit. The spec gives them 10 seconds.

### D5. Windows consoles
`multiprocessing` creates its children with no creation flags, so they attach to their parent's console, and a console-less parent is the only way to get new windows.
- **A console-less parent** is a DETACHED_PROCESS: each child would get a visible console window.
- `060` therefore uses CREATE_NO_WINDOW, whose hidden console the workers inherit.
- This change pins that behaviour with a Windows scenario, whose test starts the crawler under CREATE_NO_WINDOW itself.

### D6. The ~500k benchmark, first
- **The script:** `scripts/crawl_500k.py`, next to `scripts/writer_throughput.py`, crawls a synthetic site of up to 500,000 linked Pages with no `--max-urls` limit. It runs as a module from the repository root, `uv run python -m scripts.crawl_500k`, so it imports the site from `tests/fixture_site/` with no change to `sys.path`.
- **The site is served from its own `spawn` process** through the fixture harness, never from a thread of the crawl process, so the server's CPU and memory do not count against the crawl process's. That process keeps no request log; it returns a tally of the requests per Page, which catches a Page requested twice.
- **The site is a function, not data:** a Page's model (its Links, with their types, elements, attributes and anchors) is computed from the seed and the Page's number with `blake2b`, and its HTML is rendered from that model on each request, so the site holds no per-Page state at 500k Pages. A Page has about 450 Links of every Link type and is about 50 KB, with a header, navigation and footer repeated on every Page. A spanning tree of `fanout` children per Page (a parameter: 50 gives a depth of about 4 at 500k, 10 a deeper site) makes every Page reachable from the Seed.
- **The site is seeded:** one seed gives the same pages, Links and faults on every run, and the site's manifest records how many Pages carry each injected fault and each Issue of `040`'s v0.1 Rules, with the outcome each one should leave in `urls` (`fetch_error`, `parse_error`, `parsed`), so a run is checked by counts, not only timed. Faults sit only on leaves of the spanning tree, so none cuts off other Pages, and the count of URLs a run must account for is exact. An option adds a response latency per request.
- **A direct mode** writes the same site into a crawl file through the real store units and the writer, with no HTTP: only page preparation is replaced, by the Page model, whose rows are what preparing its HTML gives. So `040`'s Rule queries and `050`'s `summary` are measured on the real layout at 500k URLs without HTTP or page preparation; preparing 500k real Pages would take about 3.6 hours of one core. Measured on `020`'s groups 1 to 5, direct mode wrote 25.6 URLs/s at 10,000 Pages: 72% of a Page's CPU was the `urls` insert, whose value-list CHECKs cost about 100 µs a row (the diagnosis of 2026-10-14). The fix, value-list CHECKs as OR chains, is in `020` (task 7.16); after it the insert costs about 2 ms a Page in a fresh process.
- **A soak test too** (ROADMAP, Robustness rule): the site injects a share of the hostile fixtures' faults, including deeply nested `<div>` Pages over the deadline (D8) and Pages that end their worker, and a run passes only if it ends with no crash, flat memory, and every URL accounted for in `urls`.
- **Locality:** Random internal Links stay uniform over all Pages in v0.1, the harsh case for the frontier; a locality parameter is added if `080`'s sweep needs realistic frontier growth.
- **What it records:** URLs per second, peak memory of the crawl process and of each worker, machine-wide CPU and clock frequency, the crawl file's size with each table's share, the WAL peak, and the share of the crawl process's CPU time spent in page preparation.
- **Where it runs:** by hand, on a stated machine, never in CI or `scripts/check.py` (`docs/benchmarks.md`).
- **The runs:**
  - the baseline, against `020`'s in-process executor, before any pool code (task 1.2); it leaves out the Pages over the deadline and those that end their worker, which the in-process executor cannot contain
  - the crawl-file layout variants the store benchmark of 2026-10-10 left out (task 1.3, ROADMAP 026): the `links` layout, unless `030`'s task 10.1 has chosen it already, by 10.1's four layouts and decision rule, so that whichever runs first settles it once; a 16 KB page size; a zstd dictionary for stored HTML; and the WAL size of a ~100k-Page run without a concurrent reader
  - with the pool, next to the baseline (task 5.1), with these variants, each against the same run without it (decided 2026-10-14: measured here, not built in `020`):
    - a bounded `url` → id LRU cache in the writer (for example 50,000 entries, cleared when a batch rolls back), which skips the `urls_url` lookup for the navigation and footer Links every Page repeats. If it wins, `030`'s group 10 builds it, sharing the writer's rollback hook of `030`'s task 10.2 (ruled 2026-10-14)
    - in the link extractor: a cheap `//` check before `urlsplit`, skipping `urljoin` for an absolute reference already in `020`'s `NORMAL_FORM`, and `gc=False` on `DiscoveredLink`
  - **after `080`**, on the full v0.1 pipeline (ROADMAP, Build order), with the same script: it sweeps the worker count up to physical cores − 2 and keeps the count that gives the most Pages/s while the writer is never short of CPU; reports `response_headers`' share of the file, which over 10% limits that table to Internal URLs; and measures `040`'s live Issues during the Crawl (`040` D16: the full list under 30 s, `page <url>` under 1 s) and their effect on WAL checkpoints.
- **Method:** runs of variants are interleaved, each in its own process (one variant's process-wide effects otherwise reach the next, as SQLite's IN-list CHECKs slowed every later insert of their process), and the minimum is kept, each stage starts from a fresh crawl file, counts are preferred to wall time, and the rows of retracted runs stay in `docs/benchmarks.md`. The maintainer's laptop varies by up to half between runs made at different times, and its absolute numbers by about six times with its CPU state, so the script records that state (power plan, AC power, clock speed) for every run and never changes it (ruled 2026-10-14).
- **Results:** recorded in `docs/benchmarks.md`, with the machine and the commit, so later changes can compare.

### D7. The benchmark sizes the pool; it does not gate it
- The pool is built in groups 2–4 whatever the baseline shows (the user's decision of 2026-10-11). The baseline is the number the pool is compared with, and the re-run after `080` sizes it (D6).
- *Alternative:* the earlier draft's gate, building the pool only if the baseline showed page preparation as the bottleneck. Rejected by the user's decision: in the writer prototype, preparing one Page in the loop took about 26 ms, which alone caps a Crawl at a few dozen Pages per second, and the pool must land before the slice's end-to-end test.

### D8. A deadline for preparing one Page
- **Why:** lexbor parses deeply nested `<div>` elements super-linearly: 20,000 levels take 0.44 s, 100,000 levels about 80 s of CPU for a 1.1 MB page, while `<span>`, `<p>` and `<li>` stay linear (measured during `020`'s group 3, 2026-10-14). One hostile Page would hold a worker for minutes. The user chose this generic deadline over a depth pre-scan in `020` (2026-10-14), because it also covers any other slow input.
- **The deadline:** `PREPARE_DEADLINE_SECONDS = 30`, a constant of `spider.crawl.parse_pool`, with no flag, documented in `docs/architecture.md`. It runs from the moment a worker takes the Page, never from the time it waited in the queue, and it is real time measured by the executor's thread, not the context's `Clock`, because the work runs in another process. Thirty seconds is more than a thousand times a typical Page (about 26 ms in the writer prototype), lets 20,000 nested levels through, and stops 100,000. It is the same 30 seconds as the watchdog's margin over the Fetcher's deadline (`020` D16).
- **The watchdog:** it races the request only, which ends before page preparation starts, so the two never add up. If `020`'s engine ever awaits page preparation under the watchdog, its watchdog function must add this deadline.
- **Over the deadline:** the executor kills that one worker, records the URL with `parsed` = 0 and `parse_error` = `parse_timeout`, a value `020` lists (D18), and starts a replacement. The other workers and their Pages are not touched (D1).
- **The stop grace period** stays `020`'s 10 seconds: a stop ends a slow Page with its worker (D4) and does not wait for its deadline.
- *Alternative:* a regex pre-scan of the nesting depth in `020`, refusing a page above a limit before the parse. It covers one known shape only. Rejected by the user's decision.

## Risks / Trade-offs

- [Pickling large bodies to workers costs CPU] → Bodies are bytes of up to 20 MiB (`022`'s cap), and pickling bytes is a memory copy. The settings snapshot is not pickled per response (D1). The benchmark measures the overhead.
- [Worker replacements on a hostile site] → Each crash or timeout costs one worker start, about 1 second on Windows, during which the other workers go on. The benchmark's hostile share includes crashing and deeply nested Pages, so it measures the cost.
- [Worker start-up time on Windows] → It overlaps robots.txt and the Seed request, and is paid once per Crawl. A worker that needs the Public Suffix List loads it once, on its first lookup.
- [Too many workers for the writer] → Physical cores − 2 leaves two cores to the crawl process and the writer; the re-run after `080` lowers the default if fewer workers give more Pages/s. The queue bound follows the worker count, not the core count.
- [A worker that dies before it holds its pipes] → A `spawn` child that fails to import `spider.crawl.parse_pool` (its target) or the crawl process's `__main__` dies before it unpickles its pipe ends, which on Windows leaves the result pipe open in the crawl process (D1). The parent has just imported both, so this takes a broken install; a worker that has not answered "ready" within D8's deadline is therefore a `WorkerStartError` too (task 3.4), so it can never be replaced for good.
- [A process that outlives its worker holds the result pipe open] → An extractor that starts a process which inherits the worker's handles keeps the result pipe open after the worker dies, so no end of file arrives, and the Page is caught by D8's deadline instead, up to 30 seconds late. Watching each worker's process sentinel would see it at once, at the cost of a second handle per worker, which would halve the Windows cap of D1; it is rejected for a case no extractor of v0.1 makes (ruled 2026-10-14).
- [Each work item is pickled and written on the event loop's thread] → `tasks.send(work)` pickles the URL and its `FetchResult` and writes them to the worker's pipe from the loop, so a 20 MiB body (`022`'s cap) holds the loop while it is copied and written, on Windows in 8 KiB writes. The benchmark (task 5.1) judges the cost; if it stalls the loop, a sender thread per worker, or one for the pool, takes the writes off it.
- [Behaviour that no scenario names] → Group 2's review (2026-10-14) pinned it with tests beside the scenarios', in `tests/crawl/test_parse_pool.py`: the backlog of two Pages per worker; a Page refused before `start()`; a pool closed that never started; an output the crawl process cannot read, an output a worker cannot send, an outcome that cannot cross even without its outputs, and a Page whose record cannot be read, each costing only its own Page or extractor; a worker whose crawl process has ended ends quietly; a worker that ends costs only the Page it held and is replaced, also when it is ended from outside; a worker that cannot start fails the Crawl; a worker count the pool cannot run is refused; a Page cancelled while it waits is never prepared; the pool closes after a worker has ended; the worker-count table, the waiter's limit and the cgroup quota, and the default count read from faked machine facts; the default executor is the pool; and the in-process double: a crawl in the suite prepares its Pages in process, and one marked `parse_pool` in the pool. Scenario names are kept for the spec's scenarios (task 5.2), so these stay named after the behaviour they pin.

## Migration Plan

This change has no schema changes: `020` already lists the `parse_error` values `worker_crashed` and `parse_timeout`.

## Open Questions

These are deferrable, and each is additive:
- A `--parse-workers <n>` flag for machines with many cores, or for constrained containers.
- Reusing one pool across several Crawls in a long-lived MCP server.
